# Tablewise — MVP V1 Implementation

## Your Role

Act as a senior full-stack engineer, product engineer, and technical lead working on the existing Tablewise application.

Your objective is to transform the current application into a focused, customer-testable MVP, following the principles of *The Lean Startup* by Eric Ries.

**Important: This is an existing application, not a greenfield project.**

Before making changes, inspect the current implementation and reuse existing functionality wherever possible.

Do not rebuild the application from scratch.

---

# 1. Product Context

## Product Name

Tablewise

## The Customer Problem

People regularly struggle to answer:

**"What should we cook this week?"**

They spend time deciding what to cook, remembering familiar meals, and figuring out what groceries they need.

Tablewise should make that decision easier.

## MVP Value Proposition

**Plan three dinners for the coming week in approximately five minutes and automatically generate a grocery list.**

The MVP must help customers complete this experience with minimal effort.

## Our Core Hypothesis

People who struggle to decide what to cook will find enough value in Tablewise's weekly meal-planning experience that they will return to use it again the following week.

We want to validate this hypothesis with real customers.

## Lean Startup Principle

We are building a Minimum Viable Product to maximize validated learning with minimum implementation effort.

Do not add functionality merely because it seems useful.

Every implementation decision should support one of these objectives:

1. Help customers choose meals.
2. Help customers organize those meals into a weekly plan.
3. Help customers generate a grocery list.
4. Measure whether customers complete the experience and return.

Anything outside these objectives is out of scope unless necessary for security, reliability, or correct operation.

# 3. MVP Scope

## Included in MVP V1

### A. Ready-to-Use Recipe Catalog

Customers should immediately see 10–15 familiar dinner recipes.

Each recipe must include:
- Name
- Cooking time
- Ingredients
- Preparation steps
- Number of servings

Recipes should be familiar, practical, and easy to prepare.

Examples:
- Tomato pasta
- Oven-baked chicken
- Vegetable fried rice
- Baked salmon
- Chicken stir-fry
- Vegetable omelet
- Beef tacos
- Lentil soup
- Chicken and rice
- Roasted vegetables with potatoes
- Homemade pizza
- Pasta with mushrooms

Use realistic ingredients and quantities.

Recipes must be stored through the existing PostgreSQL recipe model.

Implement an idempotent seed mechanism so running it again does not duplicate recipes or overwrite customer-created data.

### B. Simplified Weekly Planner

The primary customer screen should answer:

**"What are we cooking this week?"**

Customers should be able to:
1. Browse available dinner recipes.
2. Select three recipes.
3. Assign those recipes to three different days.
4. Replace a selected recipe.
5. Change assigned days.
6. Confirm their plan.
7. Return later and see their saved plan.

The interface should be simple, calm, and intuitive.

Do not require drag-and-drop. Simple buttons and day selectors are sufficient and preferable for mobile usability.

### C. Grocery List

After planning three dinners, customers should be able to generate a grocery list.

Requirements:
- Include ingredients from selected recipes only.
- Group ingredients into understandable categories.
- Preserve quantities.
- Avoid exact duplicate entries.
- Do not incorrectly combine quantities with different units.
- Allow users to check off ingredients.
- Update the list when the meal plan changes.
- Handle missing or deleted recipes gracefully.

Reuse the existing grocery-list logic where appropriate.

### D. Browser Persistence

For MVP V1, user accounts are not required.

The weekly plan may remain in localStorage.

Requirements:
- Refreshing the page must not erase the plan.
- Returning to the application in the same browser must restore the plan.
- Plans should be associated with a specific calendar week.
- A new week should allow creating a new plan without unexpectedly overwriting the previous week's plan.
- Grocery-list checkmarks should behave predictably when the plan changes.

Do not introduce a complex authentication system for this MVP.

### E. Minimal Analytics

We need to learn how real customers use the application.

Track:

1. `planner_opened`
2. `meal_selected`
3. `plan_completed`
4. `grocery_list_opened`
5. `next_week_plan_created`

Each event should include:
- Event name
- Timestamp
- Anonymous pilot identifier
- Relevant minimal metadata, such as week identifier or selected meal count

Do not store unnecessary personal information, recipe transcripts, or sensitive data.

Use a lightweight implementation suitable for five initial test customers.

Ensure that event tracking failures never block the main customer flow.

- Running the seed process twice does not create duplicates.

## Phase 3 — MVP Planner

Build a focused MVP planning experience.

Suggested route:

`/`

You may introduce a dedicated component such as:

`client/src/pages/mvp-planner.tsx`

Requirements:

1. Show the heading "What are we cooking this week?"
2. Display available dinner recipes.
3. Let customers select up to three.

5. Let customers assign each recipe to a distinct day.
6. Allow replacing recipes.
7. Display the completed weekly plan.
8. Persist the plan in localStorage.

Acceptance criteria:
- A new customer can plan three dinners without instructions.
- The interaction works without drag-and-drop.
- No duplicate day assignments are allowed.
- The plan survives a refresh.

## Phase 4 — Grocery List Integration

Connect the new MVP planner to grocery-list generation.

Requirements:

1. Generate a grocery list from the current plan.
2. Read the correct selected recipes.
3. Group ingredients by category.
4. Preserve original ingredient information.
5. Handle duplicates safely.
6. Allow checking items.
7. Recalculate when meals change.
8. Handle deleted recipes.
9. Allow returning to the planner.

Acceptance criteria:
- Three selected dinners produce the correct grocery list.
- Replacing a meal updates the list.
- Unrelated recipes are excluded.
- Ingredient quantities are not silently lost.
- The flow works after a browser refresh.

## Phase 5 — Analytics and Week-Two Return

Implement minimal tracking.

Requirements:

1. Generate an anonymous identifier for each pilot browser.
2. Track the five MVP events.
3. Record events reliably without blocking the UI.
4. Distinguish a new week's plan from repeated activity in the same week.
5. Make it easy for a customer to plan the next week.
6. Preserve prior-week data where practical.
7. Provide a simple way for the developer to inspect aggregated pilot results without exposing raw event data publicly.

Acceptance criteria:
- We can determine how many pilot users completed a plan.
- We can determine how many opened a grocery list.
- We can determine how many planned another week.
- Tracking failures do not prevent planning.
- Analytics do not expose sensitive data.

## Phase 6 — Quality Assurance and Pilot Release

Test the complete customer experience.

Required scenarios:

1. First-time visitor opens the application.
2. Recipes load correctly.
3. Customer selects three dinners.
4. Customer assigns them to three days.
5. Customer replaces one dinner.
6. Customer confirms the plan.
7. Customer opens the grocery list.
8. Customer checks off ingredients.
9. Customer refreshes the browser.
10. Customer returns to the saved plan.
11. Customer creates a plan for the following week.
12. Customer uses the application on mobile.
13. Recipe API becomes temporarily unavailable.
14. A planned recipe is deleted.
15. Local storage contains invalid or outdated data.
16. Multiple test customers use the deployed application.

Run available TypeScript checks, builds, and relevant tests.

Fix regressions before declaring the MVP ready.

# 7. Technical Constraints

Follow these rules throughout implementation:

1. Reuse the existing React, Express, PostgreSQL, and Drizzle stack.
2. Do not introduce new frameworks without a strong reason.
3. Avoid unnecessary dependencies.
4. Do not make destructive database changes.
5. Do not overwrite existing recipes or user data.
6. Preserve compatibility with existing APIs where practical.
7. Use TypeScript types rather than `any` where feasible.
8. Validate untrusted inputs.
9. Handle malformed localStorage data safely.
10. Avoid logging full API responses or sensitive information.
11. Keep analytics endpoints appropriately protected.
12. Never expose OpenAI API keys or other secrets in frontend code.
13. Do not silently modify unrelated features.
14. Prefer small, maintainable components.
15. Add tests for important business logic where practical.

If you discover an existing issue that prevents safe MVP testing, explain it and propose the smallest appropriate fix.
